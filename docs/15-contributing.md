# Contributing

Rules for contributing to this repository. Keep changes reviewable and reversible.

## Branching

- `main` — always deployable
- Feature branches: `feat/<short-description>`
- Fix branches: `fix/<short-description>`
- Chore branches: `chore/<short-description>`
- Docs branches: `docs/<short-description>`

Never commit directly to `main`.

## Commits

Conventional Commits format:

  <type>(<scope>): <subject>

Types: feat, fix, chore, docs, refactor, perf, test, build, ci, style

Scopes: identity, warehouse, inventory, orders, deliveries, drivers,
dispatch, routing, tracking, notifications, analytics, system, events,
frontend, infra, docs

Examples:
  feat(orders): add CSV import endpoint
  fix(frontend): prevent double submit on invite modal
  docs(api): document dispatch candidate factors
  refactor(identity): extract password reset into service

Rules:
- Subject in lowercase imperative mood
- No trailing period
- Under 72 characters
- Body (optional) explains why, not what

## Pull requests

Every PR needs:
- A clear title matching the commit convention
- A short description of what and why
- Screenshots or GIFs for UI changes
- A checklist of what was tested
- CI green

PR checklist:
- [ ] `ruff check app tests` clean
- [ ] `pytest -q` passing locally
- [ ] `npm run build` passing if frontend touched
- [ ] Alembic migration included if models changed
- [ ] Docs updated if behavior changed
- [ ] No secrets, tokens, or `.env` files committed
- [ ] Changelog updated under `[Unreleased]`

Keep PRs small. If a change touches more than ~400 lines or more than two modules, split it.

## Code style

### Backend (Python)

- Python 3.11
- Line length 120 (enforced by ruff)
- Imports: standard, third-party, first-party (ruff sorts)
- Type hints on all public functions
- No wildcard imports
- f-strings only for interpolation
- Prefer composition over inheritance
- Prefer explicit over clever

Rules:
- Services accept `uow: UnitOfWork` and never open sessions
- Routers never touch the DB directly
- All errors inherit `AppError`
- All state changes write an audit row and emit a domain event
- Every mutating operation is idempotent-safe when possible

### Frontend (TypeScript)

- Strict TypeScript mode
- No `any` unless escaping a third-party type
- Types use `import type { ... }` (verbatimModuleSyntax is on)
- Components are function components
- Keep components under ~200 lines; extract subcomponents when bigger
- One file per component
- Use existing components (StatusBadge, Skeleton, Map, Toaster) before writing new

Rules:
- Pages own their queries and mutations
- Every list page has: search + filter + skeleton + empty state
- Every status in the UI uses `<StatusBadge domain="..." value="..." />`
- Use `primaryRole(user.roles)` for role checks
- Route additions go in `App.tsx` under the right layout

## Testing rules

- New endpoint → integration test in `tests/integration/`
- New service function → integration test through HTTP
- New pure function → unit test in `tests/unit/`
- New lifecycle → test both success and failure paths
- RBAC → test both allowed and forbidden
- Tenant isolation → test cross-org access returns 404 or empty

Never mock the database. Mock external providers only.

## Migrations

- Generate with `alembic revision --autogenerate -m "short message"`
- Review the autogenerated file before committing
- Never edit a migration already applied in any environment
- Additive migrations only within a release
- Use expand → migrate → contract for column changes
- Every migration needs a matching model change in the same PR

## Security

- Never commit secrets, tokens, or credentials
- Never log PII or secrets
- Validate all input via Pydantic
- All DB access goes through the ORM
- All new endpoints need RBAC consideration
- New public endpoints require justification in the PR description

## Documentation

Update docs when:
- You add an endpoint → `docs/07-api.md`
- You add a module → `docs/04-backend.md`
- You change the design system → `docs/06-ui-ux.md`
- You change deployment → `docs/11-deployment.md`
- Any behavioral change → `docs/14-changelog.md`

## Reviewing

When you review a PR:
- Read the diff before reading the description
- Question anything that touches tenant isolation
- Question any new dependency
- Question any query without an index
- Question any code without a test
- Approve only if you'd be comfortable being on call for it

## Releases

1. Changelog has an `[Unreleased]` section with all changes
2. CI is green on `main`
3. Move `[Unreleased]` to a new version heading with today's date
4. Tag: `git tag -a v0.2.0 -m "v0.2.0"`
5. Push the tag
6. Create a GitHub release with notes from the changelog

## Reporting issues

Include:
- What you expected
- What happened
- Steps to reproduce
- Environment (local, staging, prod)
- Relevant logs or screenshots

## Code of conduct

Be direct, be kind, assume good faith. Review code, not people.
